roadmap-backend · referência de arquitetura

Como o roadmapAPI é montado por dentro

Mapa completo do sistema que transforma o sumário de um livro técnico num cronograma de estudo: o esquema do banco, as classes envolvidas, o fluxo de uma chamada de ponta a ponta, o papel de cada arquivo .py e de cada arquivo que não é código, e as rotas expostas pela API.

01Modelo de dados (ER)

Três tabelas, como manda o CLAUDE.md: book guarda o que foi extraído e julgado sobre o livro; roadmap guarda um plano gerado para uma senioridade e disponibilidade; chunk guarda os trechos da web usados para achar o número de páginas. Tudo que muda de formato entre livros — capítulos, classificação, pesquisa, plano — fica em JSONB, não em tabela própria.

erDiagram
    BOOK {
        int id PK
        string hash_fonte UK "sha256 do arquivo enviado"
        string titulo
        string origem "sumario | capa"
        int paginas_conteudo "nullable"
        int paginas_fisicas "nullable, da ficha CIP"
        jsonb capitulos "lista de capitulos"
        jsonb classificacao "nullable, saida do LLM"
        jsonb pesquisa "nullable, fatos da web com fonte"
    }
    ROADMAP {
        int id PK
        int book_id FK
        string senioridade "Junior | Pleno | Senior"
        float disponibilidade_horas
        jsonb plano "cronograma + fatores aplicados"
        datetime criado_em
    }
    CHUNK {
        int id PK
        int book_id FK
        string texto "trecho web em volta de paginas"
        string fonte "URL de origem"
        vector embedding "768 dim, pgvector"
    }
    BOOK ||--o{ ROADMAP : "gera N planos"
    BOOK ||--o{ CHUNK : "acumula trechos pesquisados"
FK simples int → id, sem chave composta, sem tabela de junção. hash_fonte é o cache entre uploads: mesmo arquivo, mesmo book.id.
Por que JSONB e não tabela normalizada: capítulos, classificação e pesquisa mudam de formato a cada iteração da spec. Uma tabela Capitulo própria seria uma migration a cada ajuste, por zero ganho de query — os capítulos de um livro sempre são lidos juntos, nunca filtrados por campo interno.

Nenhuma dessas classes é ORM além de Book/Roadmap/Chunk — as demais são pydantic.BaseModel puro, sem tabela própria; viram JSONB dentro de Book/Roadmap.

03Diagrama de sequência (UML)

O caminho mais completo do sistema: gerar o roadmap de um livro cujo sumário não tem número de página, na primeira vez (cache vazio) — dispara pesquisa na web, grava a base RAG e só então classifica e calcula.

sequenceDiagram
    actor U as Usuário
    participant API as main.py
    participant DB as Postgres (book/roadmap/chunk)
    participant PES as pesquisa.py
    participant SX as SearXNG
    participant WEB as Sites (editora/livraria)
    participant OLL as Ollama (gemma4:12b / embeddinggemma)
    participant CLS as classificador.py
    participant CALC as calculo.py

    U->>API: POST /books/{id}/roadmaps {senioridade, horas}
    API->>DB: get Book(id)
    DB-->>API: book.capitulos (sem paginas)
    API->>PES: pesquisar(session, book, capitulos)
    PES->>DB: existe Chunk deste book?
    DB-->>PES: nao (primeira vez)
    PES->>SX: GET /search "titulo livro numero de paginas"
    SX-->>PES: resultados (url + snippet)
    PES->>WEB: GET cada url (trafilatura.html2txt)
    WEB-->>PES: html
    PES->>PES: trechos_de_texto() en torno de "paginas"
    PES->>OLL: embed(trechos, prefixo_documento)
    OLL-->>PES: vetores 768d
    PES->>DB: INSERT Chunk (texto, fonte, embedding)
    PES->>OLL: embed(consulta)
    PES->>DB: SELECT chunk ORDER BY cosine_distance LIMIT N
    DB-->>PES: trechos mais próximos
    PES->>OLL: chat(PROMPT_PESQUISA, schema=PaginasEncontradas)
    OLL-->>PES: PaginasEncontradas (transcrição, nunca conta)
    PES->>PES: validar() — número está no trecho citado?
    PES-->>API: Pesquisa(paginas_totais, url_fonte, avisos)
    API->>CALC: paginas_de_conteudo() + distribuir_paginas()
    CALC-->>API: capitulos com paginas estimadas
    API->>DB: book.classificacao is None?
    API->>CLS: classificar(titulo, capitulos)
    CLS->>OLL: chat(PROMPT, schema=Classificacao)
    OLL-->>CLS: Classificacao (tipo, densidade, por capitulo)
    CLS-->>API: Classificacao validada
    API->>CALC: planejar(capitulos, classificacao, senioridade, horas)
    CALC->>CALC: calcular() por capítulo + filtra por senioridade
    CALC-->>API: Plano (cronograma, excluidos, fatores)
    API->>DB: INSERT Roadmap(plano) + UPDATE book
    DB-->>API: roadmap.id
    API-->>U: 201 RoadmapCriado
Na 2ª chamada para o mesmo livro, os passos com SearXNG/Ollama-embed somem: pesquisar() lê direto da base chunk, e a classificação já está em book.classificacao.

06Por que o código cabe numa pasta só

Retomando a pergunta de antes, agora com o mapa completo dos 8 arquivos na mesa.

Com 8 arquivos e cerca de 1.100 linhas em src/, cada arquivo já corresponde a um estágio do pipeline — extracao.py, classificador.py, pesquisa.py e calculo.py são as quatro etapas da seção 2 da spec, main.py é a casca HTTP, e config.py/db.py/ models.py são infraestrutura de uma linha cada. A "organização por pasta" já existe — só que por nome de arquivo, não por subdiretório.

Isso evita import circular entre camadas artificiais (não há services/ chamando repositories/ chamando models/ só para repassar uma chamada) e deixa o sistema inteiro visível numa única listagem de diretório — o que casa com o princípio do CLAUDE.md de não criar camada que só repassa chamada, e com a regra de banco de só três tabelas sem relationship() bidirecional.

O trade-off é escala: essa estrutura para de compensar perto de uns 15–20 arquivos, quando fica difícil diferenciar "estágio do pipeline" de "utilitário genérico" só pelo nome. Como o escopo já é limitado por spec (3 tabelas, sem repository pattern, sem service layer, ver seção 5 do CLAUDE.md), não há sinal de que o projeto cresça a esse ponto — o ponto de reconsiderar seria um arquivo passando de ~300–400 linhas, onde extracao.py (296, o maior do projeto) já está chegando.
